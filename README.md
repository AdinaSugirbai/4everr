## 1. Жобаның сипаттамасы және негізгі идеясы

**4everr** — IT-ға қызығатын, бірақ қай бағытты таңдарын білмейтін оқушылар мен студенттерге арналған веб-платформа. Жүйе үш міндетті бір жерге біріктіреді: **мамандық таңдау**, **білімді тексеру** және **вакансия іздеу / орналастыру**.

Басты идея — пайдаланушыға жалпы кеңес емес, нақты жол көрсету: алдымен қызығушылығы бойынша бағыт ұсыну, содан кейін сол бағыт бойынша білімін өлшеу, әлсіз тақырыптарды көрсету және дайын болған кезде сәйкес вакансияға жеткізу.

Сайтқа кірген адам бірден өз мақсатын таңдайды (Intent Chooser): жұмыс іздеу, жұмысшы іздеу немесе мамандық таңдауға көмек алу. «Тесттер» бөлімі үш бағыттың да ортақ бөлігі болып қалады.

### 1.1. Негізгі мақсат

IT мамандығын таңдауға қиналатын адамға қызығушылығы бойынша нақты бағыт беру, содан кейін сол бағыт бойынша білімін өлшеп, келесі қадамды — оқу жолын немесе сәйкес вакансияны — ұсыну.

### 1.2. Негізгі міндеттер

1. IT мамандықтарының каталогын (Frontend, Backend, Data Science, Mobile, QA, DevOps, UI/UX) жүргізу.
2. Қызығушылық сауалнамасы арқылы мамандықты есептеп ұсыну.
3. Әр бағытқа оқу жолының картасын (қадамдар тізбегі) беру.
4. HTML, CSS, JavaScript, Java бойынша таймерлі, деңгейлі тесттер өткізу.
5. Нәтижелерді сақтап, статистика мен әлсіз тақырыптарды көрсету.
6. Мамандық таңдау мен білім тексеруді бір жүйеге біріктіру.
7. Деректерді серверде сақтау, пайдаланушы аккаунтын және контентті басқару панелін қамтамасыз ету.
8. Жұмыс іздеу мен орналастыру үшін вакансиялар бөлімін (Job Board) жасау.
9. Мамандық, тест және вакансия бағыттарын өзара сілтемелермен байланыстыру.
10. Рөлдер бойынша қолжетімділікті (қонақ, кандидат, жұмыс беруші, админ) бөлу.

### 1.3. Маңызды шектеулер

Бэкенд **Next.js ішіндегі Route Handlers** ретінде жасалады: бөлек сервер (Express, NestJS) көтерілмейді. Бэкендтің не үшін қажет екені 2-бөлімде толық түсіндірілген. Бұл бір репозиторий, бір деплой, бір тіл (TypeScript) дегенді білдіреді және 4 адамдық студенттік команда үшін ең қарапайым жол.

Жобаның **қамтымайтын** нәрселері (scope-тан тыс):

- Нақты уақыттағы чат, WebSocket.
- Төлем жүйесі.
- Бөлек микросервистер, Kubernetes.
- Мобильді қосымша (тек адаптивті веб).
- Басқа сайттардан вакансияларды көшіріп алу (парсинг). Сыртқы дереккөзден импорттау қажет болса, алдымен олардың рұқсаты мен лицензиясы тексеріледі.

## 2. Өзектілігі және шешілетін мәселе

IT саласына жаңа келген адам көбіне қай мамандықты таңдарын білмейді, білімін қалай бағалайтынын түсінбейді, ал оқуды бітірген соң жұмыс іздеуде бөлек сайттарға жүгінеді. Бұл үш қадам әдетте бір-бірімен байланыспаған құралдарда өтеді.

**4everr** осы қадамдарды бір жолға біріктіреді: *қызығушылық → бағыт → оқу жолы → тест → вакансия*.

### 2.1. Бэкенд не үшін қажет: қысқаша жауап

Жергілікті демо үшін бэкенд міндетті емес: деректі `data/*.json` файлынан оқып, нәтижені `localStorage`-та сақтауға болады, және бұл жұмыс істейді. Бірақ **4everr — демо емес, нақты пайдаланушылары бар платформа**. Оның бірнеше негізгі талабын браузер жағымен орындау мүмкін емес, өйткені браузердегі кез келген деректі пайдаланушының өзі көре және өзгерте алады.

Сондықтан бэкенд мына 4 нәрсе үшін қолданылады:

1. **Сенімділік (тест әділдігі):** дұрыс жауаптар, таймер және ұпай серверде қалуы керек.
2. **Деректі сақтау:** нәтижелер, тарих, прогресс аккаунтқа байланып, кез келген құрылғыда көрінуі керек.
3. **Бірнеше пайдаланушының ортақ деректері:** вакансиялар, өтінімдер, компаниялар, модерация. Бұл бір браузерде ешқашан жұмыс істемейді.
4. **Контентті кодсыз басқару:** сұрақ, мамандық, вакансияны админ панельден өзгерту.

### 2.2. Біздің жобаның әр талабына бэкендтің қажеттілігі

| Жобадағы талап | Бэкендсіз не болады | Бэкендпен не болады | Қатысты FR |

| Таймер шынайы жұмыс істеуі керек | Таймерді консольде тоқтатуға, уақытты өзгертуге болады | `deadlineAt` серверде есептеледі, жіберу кезінде тексеріледі (+5 секунд жеңілдік) | FR-10 |

### 2.4. Жергілікті ортада бэкенд не үшін қажет

«Егер жоба жергілікті компьютерде ғана іске қосылса, бэкенд неге керек?» деген сұраққа жауап:

1. **Жергілікті сервер — өндірістің дәл көшірмесі.** `npm run dev` Next.js бэкендін де, беттерді де бір процесте көтереді. Командадағы әр адам жобаны өндіріспен бірдей жағдайда тексереді, кейін деплойда күтпеген қате шықпайды.
2. **Қорғау (диплом/презентация) кезінде функциялар шынымен жұмыс істеуі керек.** Тіркелу, таймер, өтінім беру, модерация, админ панель комиссияға нақты жұмыс істейтін жүйе ретінде көрсетіледі. JSON + `localStorage` бұл мүмкіндіктердің көбін көрсете алмайды (бірнеше рөл, бір жерден бірнеше пайдаланушы, құрылғы ауысқанда деректің сақталуы).
3. **Бір ортада әр рөлді тексеруге болады.** Бір компьютерде кандидат, жұмыс беруші және админ ретінде кіріп, толық сценарийді (вакансия жасау → модерация → өтінім → күй) бастан аяқ өткізуге болады. Бұл тек ортақ дерекқор арқылы мүмкін.
4. **Командалық жұмыс.** Бэкенд пен фронтенд бір API келісімі (8-бөлім және Zod сұлбалары) бойынша қатар жасалады; дерекқор схемасы миграциялар арқылы бәрінде бірдей болады (`prisma migrate`, `seed`).
5. **Автотесттер.** Ұпай, таймер, рөл тексеруі, қайталанған өтінім сияқты логиканы тек серверлік код ретінде Vitest-пен тексеруге болады. Браузердегі JSON логикасын сенімді тексеру қиын.
6. **Деплойға тікелей көшу.** Локалда жұмыс істеген код өзгеріссіз Vercel + Neon-ға көшеді: тек `.env` мәндері ауысады.
7. **Қосымша Docker қажет, бірақ бөлек сервер қажет емес.** Жергілікті ортада тек PostgreSQL ғана Docker-де тұрады, бэкенд — Next.js ішінде.

### 2.5. Қабылданған архитектуралық шешім

- Бөлек сервер (Express, NestJS) **көтерілмейді**. Бэкенд — Next.js ішіндегі **Route Handlers** (`app/api/.../route.ts`). Бір репозиторий, бір деплой, бір тіл (TypeScript).
- Деректер қоры: **PostgreSQL**. Локалда Docker Compose, өндірісте Neon немесе Supabase.
- ORM: **Prisma** (схема, миграция, типтер, seed).
- JSON файлдар жойылмайды: олар `prisma/seed.ts` арқылы дерекқорды бастапқы деректермен толтыратын **seed көзі** болып қалады.
- **Қонақ режимі** сақталады: тіркелмеген адам тест тапсыра алады; сервер қолтаңбаланған токен береді, ал нәтиже уақытша `localStorage`-та тұрады және тіркелгеннен кейін серверге көшіріледі.

## 4. Негізгі функционалдық мүмкіндіктер

Талаптар жобаның толық ТЗ-сындағы `FR-n` идентификаторларымен беріледі.

### 4.1. Басты беттегі таңдау (Intent Chooser)

Басты беттің бірінші экранында 3 үлкен карточка тұрады.

| Карточка | Кімге | Қайда апарады |
|---|---|---|
| Вакансия іздеу | Жұмыс, тағылымдама іздейтін адам | `/jobs` |
| Вакансия орналастыру | Жұмыс беруші, компания өкілі | `/employer`, содан кейін `/employer/vacancies/new` |
| Мамандық таңдауға көмек | IT-ға жаңа келген адам | `/quiz-interests`, одан кейін тесттер |

## 7. Пайдаланушы жолдары және процестер

### 7.1. Негізгі сценарий

1. Пайдаланушы басты бетке кіріп, «Бағытты анықтау» батырмасын басады.
2. Қызығушылық сауалнамасының сұрақтарына жауап береді (кемінде 12 сұрақ).
3. Жүйе үздік 3 бағытты пайыздық сәйкестікпен көрсетеді.
4. Пайдаланушы бағыттың бетін ашады: сипаттама, дағдылар, оқу жолының картасы.
5. «Білімді тексеру» батырмасы арқылы сол бағытқа сәйкес тестке өтеді.
6. Тест аяқталған соң ұпай, тақырып бойынша пайыз, қателер талдауы және «қай тақырыпты қайталау керек» кеңесі көрінеді.
7. Нәтиже статистика бетінде жиналады, сәйкес вакансиялар ұсынылады.

### 7.2. Қонақтан пайдаланушыға көшу

1. Қонақ тест тапсырады, нәтиже `localStorage` ішінде `guestAttempts` кілтімен сақталады.
2. Қонақ тіркеледі немесе кіреді.
3. Клиент `POST /api/import/local` арқылы жиналған нәтижелерді жібереді.
4. Сервер әр әрекетті қайта тексереді (сұрақ идентификаторлары мен жауаптары бойынша ұпайды қайта есептейді), жарамдыларын аккаунтқа жазады.
5. Қайталануды болдырмау үшін әр әрекетте `clientId` (UUID) болады; қонақ нәтижесі қолтаңбаланған `resultToken` арқылы расталады, `clientId` ретінде `attemptId` қолданылады.
6. Сәтті импорттан кейін `localStorage` тазаланады.

### 7.3. Вакансия мен өтінім күйлері

**Вакансия күйі:** `DRAFT → PENDING → PUBLISHED → CLOSED` (қабылданбаса: `PENDING → REJECTED`, себебі жұмыс берушіге көрсетіледі).

**Өтінім күйі:** `NEW → VIEWED → INVITED` немесе `REJECTED`.

**Тест әрекетінің күйі:** `IN_PROGRESS → FINISHED` немесе `EXPIRED` (мерзімі өтсе).

### 7.4. Жұмыс беруші, кандидат және админ арасындағы өзара әрекет

| Қадам | Кандидат | Жұмыс беруші | Админ | Нәтиже |
|---|---|---|---|---|
| Вакансия жасау | — | Вакансияны жасап, жібереді | — | `PENDING` күйіндегі вакансия |
| Модерация | — | Себебін көреді (қабылданбаса) | Бекітеді немесе себебімен қабылдамайды | `PUBLISHED` / `REJECTED` |
| Іздеу | Сүзгілермен вакансия табады | — | — | Қызықты вакансия |
| Өтінім | Қысқа хат пен резюме сілтемесін жібереді | Өтінімді көреді | — | `NEW` күйіндегі өтінім |
| Қарау | Күйін өз кабинетінде көреді | Күйін `VIEWED` / `INVITED` / `REJECTED` етеді | — | Өтінім өңделді |
| Шағым | Спам не жалған вакансияға шағым береді | — | Шағымды қарайды | Вакансия тексерілді |

Бірінші вакансия модерациядан өткенше қонаққа көрінбейді. Өз вакансиясына өтінім беруге тыйым салынған.

## 9. Техникалық архитектура

### 9.1. Жалпы схема

```text
Браузер (React, Next.js клиент)
   │  fetch / Server Components
   ▼
Next.js сервері (Vercel)
 ├─ app/(pages)         — беттер (SSR / RSC)
 ├─ app/api/**/route.ts — REST API (Route Handlers)
 ├─ lib/services        — бизнес-логика (ұсыныс, ұпай, таймер, сәйкестік)
 ├─ lib/auth            — сессия, құпиясөз хэштеу
 └─ lib/validators      — Zod схемалары
   │  Prisma Client
   ▼
PostgreSQL (локалды: Docker; өндіріс: Neon / Supabase)
```

### 9.2. Ұсынылатын технологиялар

| Бөлік | Құрал | Міндеті |
|---|---|---|
| Фреймворк | Next.js (App Router) | Беттер және API бір жобада |
| Тіл | TypeScript (strict) | Типтер клиент пен серверде ортақ |
| ORM | Prisma | Схема, миграциялар, seed |
| Дерекқор | PostgreSQL 16 | Негізгі сақтау |
| Валидация | Zod | Кіріс деректерін тексеру |
| Аутентификация | Email + құпиясөз, `bcryptjs`, JWT (`jose`) httpOnly cookie ішінде | Сессия |
| Стиль | Tailwind CSS (немесе CSS Modules) | Адаптивті дизайн |
| Графиктер | Recharts | Статистика диаграммалары |
| Код сапасы | ESLint, Prettier | Тексеру |
| Тестілеу | Vitest (unit), Playwright (E2E, қосымша) | Автотест |
| Жергілікті орта | Docker Compose (PostgreSQL), `.env` | Локалды іске қосу |
| Хостинг | Vercel + Neon / Supabase | Жариялау |

Қорытынды таңдау (мысалы, Neon немесе Supabase) команда келісімімен бекітіледі.

### 9.3. Архитектуралық принциптер

- Бизнес-логика (ұсыныс, ұпай, таймер, сәйкестік) `lib/services` ішінде тұрады. Route Handler тек сұранысты қабылдап, тексеріп, сервисті шақырып, жауап қайтарады.
- Клиентке дұрыс жауаптар тест тапсырылып біткенге дейін **ешқашан** жіберілмейді.
- Барлық кіріс деректері Zod арқылы тексеріледі, қате болса `400` қайтарылады.
- JSON файлдар жойылмайды: олар `prisma/seed.ts` арқылы дерекқорды толтыратын **seed көзі** болып қалады.
- Бірыңғай API жауап форматы:

```json
{ "ok": true, "data": "..." }
{ "ok": false, "error": { "code": "...", "message": "..." } }
```

### 9.4. Деректер сущностері

| Кесте | Негізгі өрістер | Ескертпе |
|---|---|---|
| `User` | id, email (unique), passwordHash, name, role, createdAt | Құпиясөз ашық күйде сақталмайды |

| `TestAttempt` | id, userId, topicId, clientId (unique, nullable), startedAt, deadlineAt, finishedAt, score, maxScore, percent, status | Тапсыру әрекеті |

| `VacancySkill` | vacancyId, skillId, isRequired | Бар `Skill` кестесін қайта пайдаланады |

**Индекстер мен шектеулер:**

- `User.email`, `Career.slug`, `Topic.slug`, `Skill.name` — unique.
- `TestAttempt (userId, topicId, startedAt)` бойынша құрама индекс (статистика жылдам болу үшін).
- `Question (topicId, level, isActive)` бойынша индекс (тест құрастыру үшін).
- `Vacancy (status, publishedAt)` және `Vacancy (careerId, level, format)` индекстері; іздеу үшін `title` бойынша индекс (`pg_trgm` немесе `ILIKE`).
- Каскадты жою: `User` жойылса, оның `TestAttempt`, `InterestResult`, `RoadmapProgress`, `Application` жазбалары да жойылады.
- Мамандық немесе сұрақ физикалық жойылмайды, `isActive=false` қойылады: тарихтағы нәтижелер бұзылмауы үшін.

**Seed:** `prisma/seed.ts` файлы `data/careers.json`, `data/interests.json`, `data/questions.json` файлдарын оқып, дерекқорды толтырады. Қайталап іске қосқанда дубликат жасамайды (`upsert`). Кемінде: 6 мамандық, 12 сауалнама сұрағы, 4 тақырыпқа 15 сұрақтан (барлығы 60+), әр мамандыққа 5–8 оқу қадамы, 10–15 демо-вакансия.

### 9.5. Схема: деректерді өңдеу

**Клиент сұранысы → Zod тексеруі → Рөл мен иесін тексеру → Бизнес-логика (`lib/services`) → Prisma → Дерекқор → Бірыңғай форматтағы жауап.**

## 10. Алгоритмдер және бизнес-логика

### 10.1. Мамандық ұсыну алгоритмі

- Сауалнамада кемінде 12 сұрақ, әр сұрақта 4 жауап нұсқасы бар. Әр нұсқа 2–3 бағытқа салмақ береді (`OptionCareerWeight`, 0–3).
- Пайдаланушы барлық сұраққа жауап беруі керек, әйтпесе `VALIDATION_ERROR`.
- `score(c)` = таңдалған нұсқалардың осы бағытқа берген салмақтарының қосындысы.
- `max(c)` = әр сұрақтан осы бағыт үшін алуға болатын ең үлкен салмақтың қосындысы.
- `percent(c) = round(score(c) / max(c) * 100)`. Пайыз әр бағыт үшін өз шәкілі бойынша есептелгендіктен, бағыттар арасында әділ салыстырылады.
- Нәтиже: пайыз бойынша кему ретімен 3 үздік бағыт және барлық бағыттың тізімі. Тең болса, `Career.order` кішісі бірінші.
- Тіркелген пайдаланушыға `InterestResult.scores` сақталады, соңғы 5 нәтиже тарихта көрінеді.
- Салмақтар админ панелінде өзгертіледі. Сақтау кезінде тексеріледі: әр бағыттың `max(c)` мәні нөлден үлкен, ал бағыттар арасындағы `max(c)` айырмасы 2 еседен аспайды (бір бағыт әрдайым басым болмауы үшін).

### 10.2. Тест логикасы

**Тестті бастау (`/api/tests/[topic]/start`)**

- Тақырып пен оның белсенді сұрақтары табылады (`isActive = true`).
- Әдепкіде 5 оңай, 5 орташа, 3 қиын (барлығы 13) сұрақ кездейсоқ, қайталанбай таңдалады; сұрақтар мен жауап нұсқаларының реті араластырылады.
- `deadlineAt = now + topic.durationMin` (әдепкі 15 минут). Есеп тек сервер уақытымен жүреді.
- **Тіркелген пайдаланушы:** `TestAttempt` (`IN_PROGRESS`) және `AttemptQuestion` жазбалары жасалады.
- **Қонақ:** дерекқорға ештеңе жазылмайды. Сервер қолтаңбаланған `attemptToken` (HMAC, `jose`) қайтарады: ішінде `attemptId`, `topicId`, сұрақ идентификаторлары, `deadlineAt`.
- Жауапта: `attemptRef`, сұрақтар (мәтін, нұсқалар, деңгей, тип), `deadlineAt`, `serverNow`. **`isCorrect` және `explanation` жіберілмейді.**

**Клиенттегі таймер**

- Таймер `deadlineAt − serverNow` айырмасынан басталады (құрылғы сағатының қателігі әсер етпейді).
- Бет жаңартылса, тест жалғасады: тіркелген пайдаланушыға сервер, қонаққа `attemptToken` арқылы.
- Экран оқу құралдары үшін `aria-live` жаңартуы минутына бір рет жасалады.
- Уақыт бітсе, клиент қолда бар жауаптарды автоматты жібереді.

**Аяқтау (`/api/attempts/submit`)**

- Сервер `attemptRef` бойынша әрекетті табады (қонақ үшін токен қолтаңбасын тексереді).
- Мерзім: `now ≤ deadlineAt + 5 секунд` (5 секунд — желі кідірісіне жеңілдік). Кеш болса, күй `EXPIRED` болады; тіркелгенге автосақталған жауаптар бойынша, қонаққа 0 ұпаймен нәтиже жазылады.
- Жауап дұрыстығы дерекқордағы `isCorrect` бойынша тексеріледі.
- **Ұпай:** оңай = 1, орташа = 2, қиын = 3. Көп жауапты сұрақта таңдалған жиын дұрыс жиынмен дәл сәйкес келсе ғана ұпай беріледі.
- `percent = round(earned / max * 100)`. Деңгей: `< 40` — Бастаушы, `40–69` — Орта, `≥ 70` — Жоғары.
- Аяқталған әрекетке қайта жіберу `409 CONFLICT` қайтарады.
- Жауап: ұпай, пайыз, деңгей, тақырыпшалар бойынша бөліп көрсету, әр сұрақ бойынша дұрыс жауап пен түсіндірме. Қонаққа импорт үшін қолтаңбаланған `resultToken` беріледі.

### 10.3. Әлсіз тақырыптарды анықтау

- Әр сұрақтың `subtopic` өрісі бар (мысалы, CSS үшін: Flexbox, Grid, Selectors).
- Соңғы 5 әрекеттегі тақырыпша бойынша дұрыс жауап үлесі есептеледі; кемінде 3 сұрақ жиналған тақырыпша ғана бағаланады.
- Дұрыс жауап үлесі 60%-дан төмен тақырыпшалар «әлсіз» деп белгіленеді және оқу жолындағы сәйкес қадамға сілтеме беріледі (`topicTag` өрісі арқылы).

### 10.4. Статистика

- Тақырып бойынша: орташа пайыз, ең жақсы нәтиже, әрекет саны, соңғы әрекет күні.
- Динамика: уақыт бойынша пайыз графигі (соңғы 10 әрекет).
- Тақырыпшалар бойынша жылу картасы: қызыл (< 60%), сары (60–79%), жасыл (≥ 80%).
- Есептеулер `lib/services/stats.ts` ішінде, Prisma `groupBy` және агрегаттармен жасалады.

### 10.5. Вакансияға сәйкестік алгоритмі (FR-29)

- Кандидаттың дағдылары: қолмен таңдалғандар (`MANUAL`) + тесттен автоматты қосылғандар (`TEST`): тақырып бойынша нәтиже 70%-дан жоғары болса, оған байланысты дағды қосылады.
- Вакансиядағы міндетті дағдылар — `R`, қосымшалар — `O`.
- `matchPercent = round((2 * |R ∩ кандидат| + |O ∩ кандидат|) / (2 * |R| + |O|) * 100)`.
- Вакансияда дағды көрсетілмесе, сәйкестік көрсетілмейді.
- Вакансия бетінде жетіспейтін дағдылар тізімі және әр дағдыға сәйкес тест / оқу қадамына сілтеме көрсетіледі.

### 10.6. Сұрақтарға қойылатын талаптар

- Әр сұрақта: мәтін, 4 жауап нұсқасы, кемінде 1 дұрыс жауап, түсіндірме, деңгей, тақырыпша.
- Бір тақырыпқа кемінде 15 сұрақ: 6 оңай, 6 орташа, 3 қиын (13 сұрақты таңдау үшін артық қор керек).
- Сұрақтар қайталанбайды, түсіндірме қысқа әрі нақты.
- Админ сұрақты сақтағанда тексеріледі: дұрыс жауап бар ма, жауаптар қайталанбай ма.

## 12. Негізгі пайдаланушы сценарийлері

### Сценарий №1. Мамандық таңдау

**Қатысушы:** оқушы немесе студент (қонақ).

1. Басты бетте «Мамандық таңдауға көмек» карточкасын басады.
2. 12 сұрақтан тұратын сауалнамаға жауап береді.
3. Үздік 3 бағытты пайыздық сәйкестікпен көреді.
4. Бағыт бетін ашып, дағдылар мен оқу жолын қарайды.

**Күтілетін нәтиже:** пайдаланушы өз қызығушылығына сай нақты бағыт пен оқу жоспарын алады.

### Сценарий №2. Білімді тексеру

**Қатысушы:** кандидат.

1. Бағыт бетіндегі «Білімді тексеру» батырмасы арқылы тестке өтеді.
2. Таймермен 13 сұраққа жауап береді.
3. Нәтиже бетінде ұпай, деңгей, қателер талдауы мен түсіндірмелерді көреді.
4. Статистика бетінде әлсіз тақырыптар мен оқу жолындағы сәйкес қадамдарды табады.

**Күтілетін нәтиже:** пайдаланушы қай тақырыпты қайталау керегін біледі, прогресі аккаунтта сақталады.

### Сценарий №3. Қонақтан кандидатқа көшу

**Қатысушы:** қонақ.

1. Тест тапсырады, нәтиже браузерде сақталады.
2. Тіркеледі немесе кіреді.
3. Жүйе нәтижелерді серверде қайта тексеріп, аккаунтқа көшіреді.

**Күтілетін нәтиже:** нәтижелер жоғалмайды және қайталанбайды.

### Сценарий №4. Вакансияға өтінім беру

**Қатысушы:** кандидат.

1. Басты беттен «Вакансия іздеу» арқылы `/jobs` ашады.
2. Деңгей, формат, қала бойынша сүзгі қолданады.
3. Вакансия бетінде сәйкестік пайызын және жетіспейтін дағдыларды көреді.
4. Өтінім береді, күйін `/me/applications` бетінде бақылайды.

**Күтілетін нәтиже:** кандидат өз деңгейіне сай вакансияға өтінім береді және процесті қадағалайды.

### Сценарий №5. Вакансия орналастыру

**Қатысушы:** жұмыс беруші және админ.

1. Жұмыс беруші «Мен жұмыс берушімін» ретінде тіркеліп, компания профилін толтырады.
2. Вакансия жасайды; ол `PENDING` күйіне түседі.
3. Админ вакансияны бекітеді немесе себебімен қабылдамайды.
4. Жарияланған вакансияға келген өтінімдерді жұмыс беруші қарап, күйін өзгертеді.

**Күтілетін нәтиже:** вакансия модерациядан өтіп жарияланады, өтінімдер бір жерде өңделеді.

| Сессияны ұрлау | JWT (HS256), httpOnly, Secure, SameSite=Lax cookie, мерзімі 7 күн; құпия кілт тек ENV-де |
| CSRF | SameSite=Lax + барлық POST / PATCH / DELETE сұраныстарында Origin тексеру |
| Дұрыс жауаптың сыртқа шығуы | Prisma `select` арқылы `isCorrect`, `explanation` тест барысында шығарылмайды; unit-тестпен бекітіледі |
| Ұпай жалғандығы | Ұпайды тек сервер есептейді, клиент тек таңдалған жауап идентификаторларын жібереді |
| Уақытты алдау | Дедлайн сервер уақытымен; қонақ токені қолтаңбаланған |
| Brute-force, спам | Rate limit: login 5/мин (IP+email), register 5/сағ, тест бастау 20/сағ; вакансия жасау 5/тәулік, өтінім 20/тәулік, шағым 10/тәулік |
| SQL injection | Prisma параметрленген сұраныстары; шикі SQL қолданылмайды |
| XSS | React автоматты экрандауы; `dangerouslySetInnerHTML` қолданылмайды; вакансия мәтіні тек таза мәтін немесе шектеулі Markdown, сілтемелер `rel="nofollow noopener"` |
| Рұқсатсыз қол жеткізу | `middleware.ts` `/admin`, `/api/admin` үшін; әр handler ішінде иесі мен рөлін қайта тексеру |
| Жұмыс берушілер деректері | Жұмыс беруші тек өз компаниясы, вакансиялары және солардың өтінімдерін көреді |
| Кандидат деректері | Email мен резюме сілтемесі жұмыс берушіге тек өтінім бергенде ашылады; аккаунт жойылса, өтінімдер де жойылады |
| Жалған вакансиялар | Алғашқы вакансия міндетті модерациядан өтеді; бетте «Алдын ала төлем сұраған жұмыс берушіден сақ болыңыз» ескертуі; шағым беру мүмкіндігі |
| Құпия деректердің репозиторийге түсуі | `.env` `.gitignore` ішінде; тек `.env.example` қосылады |
| HTTP тақырыптары | `next.config.ts` арқылы `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, негізгі CSP |
| Тәуелділіктердегі осалдықтар | `npm audit` CI ішінде, айына бір рет жаңарту |
| Жеке деректер | Тек email және аты сақталады; пайдаланушы `DELETE /api/auth/me` арқылы аккаунтты жоя алады |

## 15. Жергілікті орта және іске қосу

Бэкенд өз компьютерде іске қосылады: бөлек сервер қажет емес, Next.js бір процесс ретінде бет пен API-ды бірге береді. Тек дерекқор қосымша қажет.

### 15.1. Не орнату керек

| Құрал | Нұсқа | Не үшін |
|---|---|---|
| Node.js | 20 LTS және одан жоғары | Next.js, Prisma |
| npm | Node-пен бірге | Тәуелділіктер |
| Git | кез келген жаңа нұсқа | Репозиторий |
| Docker Desktop | соңғы нұсқа | Жергілікті PostgreSQL |
| VS Code + Prisma, ESLint кеңейтімдері | қалауынша | Ыңғайлы жұмыс |

Docker орнату мүмкін болмаса, балама: Neon сайтында тегін dev дерекқор жасап, оның сілтемесін `DATABASE_URL`-ға салу.

### 15.2. `docker-compose.yml`

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: everr
    ports:
      - 5432:5432
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

### 15.3. Ортаның айнымалылары (`.env.example`)

| Айнымалы | Мысал | Сипаттама |
|---|---|---|
| `DATABASE_URL` | `postgresql://app:app@localhost:5432/everr` | Дерекқорға қосылу |
| `DIRECT_URL` | локалда сол мән | Миграция үшін тікелей қосылу (өндірісте pooler-сіз сілтеме) |
| `AUTH_SECRET` | кемінде 32 символдан тұратын кездейсоқ жол | Сессия мен тест токендерін қолтаңбалау |
| `NEXT_PUBLIC_APP_URL` | `http://localhost:3000` | Origin тексеруі үшін |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | өз мәндерің | Seed алғашқы админді жасайды |
| `RATE_LIMIT_ENABLED` | `true` | Жергілікті дамытуда `false` қоюға болады |

`.env` файлы `.env.example` көшірмесінен жасалады және репозиторийге түспейді.

### 15.4. Алғашқы іске қосу

```bash
git clone https://github.com/AdinaSugirbai/4everr.git
cd 4everr
git checkout dev
cp .env.example .env
docker compose up -d
npm install
npx prisma migrate dev
npx prisma db seed
npm run dev
```

Содан кейін браузерде `http://localhost:3000` ашылады. Дерекқорды көру: `npx prisma studio`.

### 15.5. npm скрипттері

| Скрипт | Не істейді |
|---|---|
| `npm run dev` | Жергілікті сервер |
| `npm run build` | Өндірістік құрастыру (алдында `prisma generate`) |
| `npm run lint` | ESLint тексеруі |
| `npm test` | Vitest тесттері |
| `npm run db:migrate` | `prisma migrate dev` |
| `npm run db:seed` | Бастапқы деректерді жүктеу |
| `npm run db:studio` | Prisma Studio |
| `npm run db:reset` | Дерекқорды тазалап, қайта миграциялап, seed жүргізу (тек локалда) |

### 15.6. Жиі кездесетін мәселелер

| Мәселе | Шешімі |
|---|---|
| `ECONNREFUSED 5432` | Docker іске қосылмаған: `docker compose up -d` |

| Схема өзгерген, бірақ типтер ескі | `npx prisma generate` |
| Порт 3000 бос емес | `npm run dev -- -p 3001` |

## 16. Тестілеу және жариялау

### 16.1. Тестілеу

| Деңгей | Не тексеріледі | Құрал |
|---|---|---|
| Unit | Ұсыныс алгоритмі, ұпай есептеу (single / multiple), деңгей шекаралары, дедлайн және 5 секундтық жеңілдік, әлсіз тақырыпты анықтау, вакансия сәйкестігінің формуласы | Vitest |
| Integration | Тіркелу-кіру, қайталанған email, тест бастау жауабында `isCorrect` жоқтығы, басқа адамның нәтижесіне қол жеткізу (403), қайталап жіберу (409), импорт қайталануы, басқа жұмыс берушінің өтінімдеріне қол жеткізу (403), өтінімнің қайталануы (409), модерацияға дейін вакансияның жасырын болуы | Vitest + жеке тест дерекқоры |
| E2E (қосымша) | Сауалнама → ұсыныс → бағыт беті → тест → нәтиже → статистика | Playwright |
| Қолмен | Мобильді көрініс, таймер, бетті жаңартқанда тестті жалғастыру, интернет үзілуі | Чек-парақ |

Кем дегенде бизнес-логика (`lib/services`) тесттермен 80% жабылуы керек.

### 16.2. Жариялау (деплой)

1. Neon (немесе Supabase) ішінде өндірістік дерекқор жасау: `DATABASE_URL` үшін pooled сілтеме, `DIRECT_URL` үшін тікелей сілтеме.
2. GitHub репозиторийін Vercel-ге қосу: `main` — Production, `dev` және PR-лар — Preview.
3. Vercel-де ENV мәндерін енгізу: `DATABASE_URL`, `DIRECT_URL`, `AUTH_SECRET` (өндіріс үшін жаңа кілт), `NEXT_PUBLIC_APP_URL`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`.
4. Build командасы: `prisma generate && prisma migrate deploy && next build`.
5. Бірінші деплойдан кейін seed бір рет жүргізіледі.
6. Preview ортасы үшін бөлек дерекқор бұтағы (Neon branch) қолданылады.
7. Жарияланғаннан кейін тексеру: `/api/health`, тіркелу, кіру, сауалнама, тест, статистика, вакансиялар, админ панель.
8. Домен (қалауынша) және HTTPS Vercel арқылы автоматты қосылады.

## 19. Күтілетін нәтиже

Әзірлеу нәтижесінде мамандық таңдауды, білім тексеруді және жұмыс іздеуді біріктіретін веб-платформа алынады. Пайдаланушы қызығушылығы бойынша бағыт алады, оқу жолымен жүреді, білімін серверлік таймерлі тесттермен өлшейді, әлсіз тақырыптарын көреді және дайын болған кезде сәйкес вакансияға өтінім береді. Жұмыс берушілер вакансия орналастырып, өтінімдерді бір жерде өңдейді.

### 19.1. Қорытынды процесс — мысал

**Бастапқы жағдай:** 10-сынып оқушысы IT-ға қызығады, бірақ бағытты білмейді.

| Қадам | Нәтиже |
|---|---|
| Сауалнама | Үздік 3 бағыт пайыздық сәйкестікпен (мысалы, Frontend, UI/UX, QA) |
| Бағыт беті | Сипаттама, дағдылар, оқу жолының картасы |
| Оқу жолы | Нөмірленген қадамдар, орындалғандарын белгілеу |
| TechTest | HTML / CSS / JavaScript бойынша деңгейлі тест, ұпай және деңгей |
| Әлсіз тақырыптар | Flexbox бойынша 60%-дан төмен, оқу қадамына сілтеме |
| Вакансиялар | Тағылымдама және Junior вакансиялары, дағдыға сәйкестік пайызы |
| Өтінім | Қысқа хат арқылы өтінім беру және күйін бақылау |

### 19.2. Қорытынды концепция

**4everr — бұл жай тест немесе вакансия сайты емес, IT-ға жолды қызығушылықтан бастап жұмысқа дейін көрсететін біртұтас жүйе.**

Негізгі принцип:

**Қызығушылық → Бағыт → Оқу жолы → Білімді тексеру → Әлсіз тақырыптарды жабу → Вакансия → Өтінім.**

## 20. Ағымдағы мәртебе және ашық сұрақтар

Қазіргі уақытта құжат жобаның **концепциясы мен жоспарланған функционалдығын** сипаттайды. Көрсетілген модульдер, кабинеттер және алгоритмдер кейінгі әзірлеуге арналған талаптар болып табылады, олардың дайын екені туралы мәлімдеме емес.

Әзірлеу басталғанға дейін команда бекітуі керек:

- Дерекқор: Neon, Supabase немесе басқа? (Ұсыныс: Neon, себебі Vercel-мен жақсы жұмыс істейді.)
- Админ панель бірінші нұсқаға кіре ме, әлде алдымен JSON + seed арқылы өзгертіп, кейін жасаймыз ба?
- Кіру әдісі: тек email / құпиясөз бе, әлде Google-мен де?
- Қонақ тесті сақталсын ба (7.2), әлде тест тапсыру үшін тіркелу міндетті ме? Соңғысы жеңілірек.
- Вакансиялар нақты ма (нақты жұмыс берушілер қосады), әлде қорғау үшін демо-деректер ме?
- Өтінім беру сайт ішінде ме, әлде вакансияда сыртқы сілтеме (компания сайты, Telegram, email) болса жеткілікті ме? Соңғысы әлдеқайда жеңіл.
- Модерацияны кім жасайды (команда мүшесі админ ретінде)?
- Жұмыс беруші компания растауы (верификация) қажет пе, әлде бірінші нұсқада админ қолмен ме?
- Бастапқы нарық: тек Қазақстан (теңге, қалалар тізімі) ма?
- Қорғау күні және аралық тапсыру мерзімдері (13-бөлімдегі кезеңдерді соған сай түзету).

**Қазіргі мақсат — 4everr жобасын командалық әзірлеуге арналған техникалық тапсырманы дайындау және келісу.**
